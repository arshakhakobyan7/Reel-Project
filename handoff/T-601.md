## What to build
1. `ConsentProvider` (ABC) with `name` and
   `check(group: str, lesson_date: date | None) -> ConsentDecision`. `ConsentDecision`: overall
   `ConsentResult`, `group_ref`, per-student entries (student id + status only — no names, emails
   or other personal data), and a human-readable `message`.
2. Mapping (document it in the contract and docstring): every student granted → `passed`; any
   denied → `opted_out`; any student with unknown/missing status → `opted_out` (D-019);
   group not known to the registry → `unknown`; timeout, connection error, 5xx, malformed
   response → `unreachable` (the stage will retry, then hold). 4xx auth errors: decide, document,
   test.
3. File provider: JSON keyed by group name (case-insensitive) with student statuses; a missing or
   invalid file must give a clear error result, not a crash. Read the file on every check (staff may
   edit it while Reel runs).
4. HTTP client: base URL and timeout from settings; bearer token from `CORE_ENGINE_API_TOKEN`
   (never logged); JSON only; validate the response shape strictly.
5. Contract doc: endpoint(s), request/response JSON examples, status codes, auth, what Reel stores,
   privacy note. Keep it short and concrete.

## Acceptance criteria (from TASKS.md) — each needs a test
- HTTP client against the mock server: granted, denied, unknown, timeout, 5xx (+ malformed JSON);
- file provider (valid, group missing, file missing, invalid JSON);
- an unknown student status counts as opted out (D-019);
- `make_consent_provider` picks the provider from config.
Timeout tests must be fast (use a tiny timeout, e.g. 0.2 s).
