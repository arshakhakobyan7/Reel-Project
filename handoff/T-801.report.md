## Design and public API

```text
StaffNotifier(db: Database, cfg: LoadedConfig, client: SlackClient | None = None,
              clock: Callable[[], datetime] = utcnow, *, poll_interval: float = 30.0,
              history_page_size: int = 100, max_history_pages: int = 100)
StaffNotifier.run_once() -> int
StaffNotifier.run(stop: threading.Event) -> None
```

The package exports StaffNotifier. run_once returns the number of relevant events
completed (live delivery, confirmed crash recovery or dry-run logging). Initialization,
idle passes and events skipped by filters/permanent errors do not increase the count.
The default clock is reel.db.utcnow; logs include its ISO notification_at value.

State is stored in the existing AppMeta table, without a migration:

- notifications.last_event_id: decimal event id as text. On the first run, initialized
  to MAX(job_events.id), or 0 if empty, inside a short immediate transaction. No history
  is sent. On later runs, events above this watermark are consumed in id order.
- notifications.pending_event: absent by default; while a relevant event is pending,
  contains JSON with event_id, job_id, stage, kind, redacted/escaped text, destination
  channel, original mode and database instance_id. It is deleted on acknowledgement.

A pending payload is committed before Slack I/O. No database writer transaction spans
network calls. After delivery, watermark advancement and pending deletion happen
atomically in their own short transaction. Irrelevant/disabled events advance the cursor;
a retryable error leaves the pending event and does not advance through that event.
A permanent Slack error is logged and acknowledged/skipped so later events can proceed.

Live delivery uses T-703's SlackClient, channel-ID validator, timestamp validation and
render_message escaping. Before posting, cursor-paginated channel history is searched
for the same alert metadata. This recovers a successful post whose response or local
acknowledgement was lost, avoiding another message after restart. Unverifiable/incomplete
history fails closed. Instances in one process share a per-database lock to avoid racing.

Metadata contains event_type=reel_staff_alert and event_payload.job_id/event_id, plus
the database instance_id namespace so messages from a different database are not mistaken
for the current event. The stable pending payload survives later changes to job fields.

Events are selected by notifications.events:

- failed: EventKind.FAILED; uses immutable event stage/message/attempt data before mutable
  job fallbacks, so a re-run does not replace the original failure evidence.
- on_hold: EventKind.HELD; includes the event's reason and message, retaining consent or
  identification details even if the job has since been released.
- flagged: EventKind.STAGE_COMPLETED for import/transcribe with nonempty flags.
  event.data.flags is authoritative when present, including an explicit empty snapshot.
  Legacy events without the key use job.flags at first outbox observation. See the
  required producer follow-up below for exact event-time behavior.

Messages have short Armenian headings, group/lesson or the source file's basename,
stage, error/reason/flags, attempts for failures, and web.base_url/jobs/{job_id}.
Absolute source paths are not exposed. Dynamic values are Slack-escaped using T-703;
known secrets from cfg.secrets and standard token patterns are redacted before storing,
sending or logging the alert. Diagnostic exceptions are not logged with raw tracebacks.
Every completed notification is logged through reel.notify.

Dry-run writes only logs/outbox progress and never calls HTTP/history. It needs no token
or channel. Current dry-run mode also suppresses retries of a previously prepared live
alert. A pending dry-run preview is never turned into a real post by switching to live.
Current event filters apply to pending retries too. Live construction requires a valid
channel ID and a present/valid SLACK_BOT_TOKEN from the existing secrets loader.

run(stop) drains passes then uses stop.wait(poll_interval), making idle shutdown
interruptible. Unexpected pass errors are logged by exception type and retried on a
later poll, with pending state retained. The existing worker Attention callback is not
used as a second notification source; committed JobEvents are authoritative.

## Requested changes

1. **Required for exact event-time flags:** in src/reel/queue/jobs.py, JobQueue.complete,
   add `flags=list(job.flags)` to the `_record(...)` call for the completed stage,
   alongside attempt and seconds. Current JobQueue.complete records no flags snapshot,
   so an asynchronous consumer cannot reconstruct flags that changed before it polled.
   This consumer already honors the new event.data.flags value. Legacy current-state
   fallback is explicit; it is not claimed to recover unavailable historical evidence.
   The shared queue file was not modified because handoff/README.md forbids that.

2. **Before event retention/deletion is introduced:** JobEvent currently has an ordinary
   SQLite integer primary key, without AUTOINCREMENT. Deleting the newest/all events
   can reuse ids below the watermark. Add `_NO_ID_REUSE` to JobEvent's table options
   and the corresponding schema migration before purging these events (or guarantee
   job_events remains append-only). This is needed to retain an id-only watermark's
   durability after deletion; no schema changes were made here.

3. **Runtime integration belongs to Claude/T-901:** start one StaffNotifier.run(stop)
   consumer process per database, bootstrapping before starting producers when setting
   up notifications for the first time. Do not also send Slack messages directly from
   the Worker Attention hook for the same transitions. No worker/CLI/runtime files
   were changed. No new config keys or dependencies are required.

## Open questions and known limits

- All new consumer tests and full checks pass. The producer-side flags snapshot above
  remains a shared-file follow-up for fully exact historical flagged notifications.
- No live Slack workspace was contacted; the client/transport comes from reviewed T-703.
  History access/metadata visibility is required for crash recovery. A message hidden
  by Slack retention cannot be found; recovery cannot provide an unconditional
  distributed exactly-once guarantee once that evidence is unavailable.
- One consumer process per database is required. The process lock covers instances and
  threads, not multiple independent processes performing the same history/post race.
- History uses configurable constructor bounds (100 pages of 100 by default); incomplete
  scans stop safely rather than post blindly. Polling provides the retry interval;
  run_once does not sleep internally or implement a separate backoff scheduler.
- Existing pending text/channel are retained across retries. Current dry-run and event
  filters can suppress delivery. A failed/held event's stage/message/reason/attempts
  come from event data where available, while group/lesson identify the job when first
  materialised. Text values are clipped to keep staff alerts short.
- Logging and a DB acknowledgement are separate side effects: a crash between them
  may repeat a log line. Slack history recovery prevents another post while the
  original message/metadata remains visible. A dry-run is never reported as a live send.
- Idle stop is prompt; a current run_once pass/in-flight Slack operation finishes before
  the outer loop exits. Corrupt persisted outbox state raises a clear error for repair
  rather than silently resetting the watermark or replaying history.
